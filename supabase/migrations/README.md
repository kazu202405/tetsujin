# マイグレーションを書くときの決まり

## 🔴 関数を手で打ち直さない

`CREATE OR REPLACE FUNCTION` は**関数の全文を置き換える**。1単語だけ直したいときも、
書くのは100%の書き換えになる。∴ 記憶や理解から組み立て直すと、
**書き写さなかった部分がそのまま機能の削除になる。**

エラーは出ない。Postgres は「文法として正しく、前より仕事をしない関数」を
何の文句も言わずに受け入れる。テストも型チェックも無い。

### 実際に起きたこと

- **2026-08-31**: 通知の文言を変えるだけのつもりで `send_connection_request` を
  打ち直し、**再申請のクールダウン（断られてから90日は再申請できない）を丸ごと落とした。**
  戻り値の型を間違えて `42P13` で弾かれたおかげで表に出たが、
  そこを合わせていたら静かに適用されていた。
- 以前にも同じ形で、決済列の保護が本番で5日間外れていた。

### 手順

1. 直したい関数の**現物**を持ってくる。
   - 本番の現物：SQL Editor で `SELECT pg_get_functiondef('public.関数名'::regproc);`
   - ファイルから取るなら、**最後にその関数を定義したマイグレーション**から。
     （途中のファイルを見ると、後から足された行を落とす）
2. **機械的に複製**して、変えたい箇所**だけ**を差し替える。
3. 引数と戻り値が元と1文字も違わないことを確かめる。
   違うと `42P13 cannot change return type` か、
   **古い版が残ったまま新しい版が増える**（どちらが呼ばれるか分からなくなる）。

### 戻り値や引数を変えるときは DROP してから

`CREATE OR REPLACE` では列を増やせない。先に
`DROP FUNCTION IF EXISTS public.関数名(引数の型...);` を書く。
`GRANT` も一緒に消えるので付け直すこと。

## 🔴 消す前に、使われているか DB 側で数える

画面で数えて0件だったから消す、では**数えた後に誰かが選んだ場合**を取りこぼす。
判定は関数の中でやる（例：`admin_delete_matching_option`）。

## 🔴 画面のボタンを消しても塞がらない

anon キーで PostgREST を直接叩ける。**権限は必ず RLS か
SECURITY DEFINER 関数の中で判定する。** 画面と API の出し分けは
「押せなくする」「理由を出す」ためのもので、守っているのは DB 側。

## 通知の文面について

文面が関数の中にあるので、「◯◯さん」の一言を変えるだけで
権限チェックごと書き直すことになる。**他の理由でその関数を触るときに、
ついでに文面を外へ出す**方針（2026-08-31）。
まとめて27箇所やると、上の事故を27回繰り返すことになるので、一度にはやらない。
